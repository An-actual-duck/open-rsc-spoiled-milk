Browser middle input and current graphics controls
=================================================

Scope
-----
Focused fix/browser-controls-settings, worker ai2. Desktop/native input paths,
settings defaults, native GLFW/window capability and public service unchanged.
Browser readiness/Bridge/WebGL rendering changes belong to the separate ai1
worker. Browser.js edits are narrow module import/creation/native merge/disposal,
proof counters and sticky input error reporting, coordinated with that worker.

Root causes
-----------
1. RendererSettingsPanel.State only considered the native OpenGL primary window.
   A genuine browser GPU backend therefore got legacy software scaling rows,
   hiding the current renderer's working lighting/shadow/material controls.
2. Existing ORSCApplet MouseHandler already handles Java MouseEvent.BUTTON2
   independently from gameplay clicks. Official CheerpJ5.0 runtime cj3.js input
   normalization rejects finite event.buttons values greater than2; DOM middle
   uses button1/buttons4. Middle press/drag was discarded before reaching AWT.

Primary references inspected (no vendor code copied or patched):
  https://cjrtnc.leaningtech.com/5.0/cj3.js
  https://cheerpj.com/docs/guides/implementing-native-methods
  https://developer.mozilla.org/en-US/docs/Web/API/MouseEvent/buttons
  https://docs.oracle.com/javase/8/docs/api/java/awt/event/MouseEvent.html

Settings
--------
State has a separate browserGpu capability using the installed optional browser
backend, never enabling native LWJGL/GLFW/window flags. Browser Graphics includes
Middle mouse, Lighting, Shadows, Geometry, Terrain Variation, Fog, terrain/object
shading, brightness/dimness, contrast, gamma, saturation, and server-supported
visibility controls. Existing action adapters retain settings/persistence and
gameplay authority. Uniform/lighting exporters already read these settings live.

Browser Geometry cycles Smooth <-> Faceted; desktop keeps Smooth/Faceted/Wire.
A legacy saved Wire preference already renders filled faceted triangles in
WebGL, so the browser labels it Faceted and its next filtered cycle normalizes
to Smooth. No unsupported polygon-line rendering is offered. Native window mode,
aspect/render-surface changes, native profile bundles (which change window and
surface), and software-only scaling controls are omitted rather than exposed as
ineffective or unsafe browser controls. No browser fullscreen/resizing feature
was added. Material changes can require several budgeted repack frames.

Color/relief controls retain desktop semantics: they adjust the world renderer,
not HUD colors or all actor sprites. Roof hiding retains physical roof shadow
casters just as the native renderer does.

Middle relay and lifecycle
--------------------------
New browser-middle-mouse.js captures only middle gestures within the displayed
GPU viewport. It preserves DOM button1/buttons4 in bounded proof counters,
prevents browser autoscroll/paste/auxclick and duplicate vendor input, and queues
press/drag/release/cancel packets. Left/right and keyboard paths stay ordinary.
Move packets coalesce, queue length is bounded64, overflow cancels safely, and
only one native consumer can wait. There is no idle polling: a dedicated Java
daemon waits on the native Promise until input/disposal is available.

BrowserMiddleMouseInput validates bounded four-int packets, converts game-local
viewport coordinates to applet coordinates by ADDING current screen offsets
(the existing handler subtracts them), creates ordinary AWT BUTTON2 events,
and dispatches through the existing handler on the EDT with backpressure.
The existing orbit owns camera yaw, tilt/classic zoom and gameplay-button
suppression. No separate camera formula or direct player movement is introduced.

Blur, hidden page, pointer cancellation/lost capture, readiness false or Stop
release the gesture. New presses obey browserWorldInputAllowed; release/cancel
of an active gesture still work while gated. Readiness worker dispatches
browser-world-readinesschange on gate changes to cancel stationary held input.
Stop resolves the outstanding wait with a clean sentinel; Java finally releases
any orbit. Expected dispatch exceptions become sticky inputError status, so
periodic loop/FPS messages cannot conceal a dead relay. Critical Error subclasses
are not swallowed. The original one-off desktop-wide keyboard report remains
undiagnosed and is not claimed fixed by this work.
