Versioned deployment and executable filesystem
----------------------------------------------
Root index.html references /assets/<build-id>/session.js; that module locates its
runtime iframe relative to import.meta.url. CheerpJ /app is the ORIGIN root, so
classpath and bootstrap source paths explicitly use /app/assets/<build-id>/.
The public Java helper permits only that bounded prefix shape. Initial assets are
copied into the existing /files game layout; user settings remain client-owned.
Official filesystem documentation: https://cheerpj.com/docs/guides/filesystem

scripts/browser-gameplay/package-public-alpha.py requires a fresh clean exact-HEAD
full client receipt plus source/class/asset manifests, a complete1330-sector GPU
catalogue, complete1400-resource compact derivative and445-recipe/1330-query RAM
cook bound to the same JAR/source/assets/settings. Source-only or rebound old cooks
are refused. It compiles a fresh deterministic browser-spike.jar and emits a
versioned static directory plus external package-receipt.json. No services start.

Only maintained HEAD audio *.wav/sounds.mem and the closed six video/archive paths
are copied, each checked against committed bytes (currently44files/4,875,269bytes).
Untracked caches/backups, credentials, test account data and private fixture config
are excluded. Source attribution/LICENSE are versioned with the build. Runtime
packaging has no output-art fallback. Canonical manifest/source metadata/textures
remain, but unused112-byte canonical geometry binaries are omitted: the validated
complete compact sidecar replaces every geometry resource before any fetch, and
public mode cannot select legacy format. All1400compact geometries remain.

web/public-release.json schema1 declares origin, websocket, preset, build IDs,
client/source hashes, assetPrefix, every served payload path/length/SHA256,
SHA256SUMS hash and original cook identities. SHA256SUMS and public-release.json
are excluded from the payload list to avoid circular hashes; the external package
receipt pins public-release.json itself. Hosting independently verifies the exact
manifest and full inventory. Root entry files require no-cache; versioned assets
require immutable caching and HTTP Range support. Old build IDs must remain
reachable for already-open sessions when current changes.
