Terrain rendering and world loading plan
=======================================

Improve terrain consistency, travel, and rendering headroom in the browser
and standalone clients. Start with a measured region-crossing route and a
small vertex-reuse prototype. Keep the tile map as the source of truth.

Evidence
--------

The v0.3.25 browser audit covered all 1,400 static geometry chunks. Within
each chunk, sharing byte-identical vertices preserved every indexed attribute
and triangle order. With 32-bit indices, estimated vertex and index storage
fell 29.17% for terrain, walls, and roofs, 17.60% for static scenery, and
about 21.5% across the catalogue. The audit measured geometry bytes. Travel time,
GPU memory in use, and FPS still need an in-game comparison.
Evidence lives under output/diagnostics/terrain-pipeline-audit/v0325/.

Private persistent overworld experiment
--------------------------------------

The private full-residency mode uploads the whole compact overworld
catalogue at entry. A persistent static terrain selection derives its
window from the absolute camera position. The same resident geometry
identities survive camera travel and changes to the gameplay region
origin. When walking, scenery retains the authoritative rows for
live and changed objects. The production renderer keeps its default
bounded policy.

The detached camera demonstration selects authored terrain and
scenery directly from the resident catalogue. The test account stays
put. The flyover omits actors and local lighting masks. The matching
walking mode retains actors, normal lighting and gameplay authority.

On one matched walking route both modes held all 1,400 catalogue
entries, with 988,074,828 bytes of resident geometry. The layout with
the original region selection paused for 526 ms outbound and 286 ms
on return. Camera-based terrain selection measured 495 ms and 341 ms.
Both sent real region transitions for the gameplay scene. The test
therefore leaves the gameplay transition on the path to a new frame.
The full-residency login still requires checked CPU and graphics
readiness, with no bounded residency gate when full mode is selected.

The 20-second flyover replay crossed two old boundaries while the
player position and gameplay scene epoch stayed fixed. All 1,400
geometry entries stayed resident, with zero additional catalogue
downloads. The sampled boundary frame intervals were 22 and 24 ms.
The renderer continued to report ordinary uploads outside the static
catalogue. The replay and comparison are under output/diagnostics/
browser-persistent-world/ in the worker checkout.

Live walking handoff
--------------------

A Firefox replay on the private world walked across the boundary near
(144, 644, 0) in both directions using the same map, options, and route.
The server reached the same waypoints in both runs. Both held all 1,400
catalogue entries and downloaded zero new catalogue bytes during travel.

The prepared walking prototype keeps the active scene until authoritative
player and static receipts finish. Same-scope global level 0 walking can
release the first assembled frame once it has the current immutable
prepared terrain, matching scenery revision and origin, and no pending
terrain presentation product. Other transitions keep the two-sample
stability check. WebGL still waits for the scene's required geometry.
The prototype is opt-in with preparedwalk=on in private full-residency mode.

                                    Existing   Prepared walk
  Fresh frame gap, outbound           512 ms      480 ms
  Fresh frame gap, return             286 ms      284 ms
  Receipts to Java release, outbound  180 ms      141 ms
  Receipts to Java release, return    106 ms       92 ms
  First full WebGL bridge, outbound   138 ms      146 ms
  First full WebGL bridge, return     114 ms      120 ms
  Stationary frame median              20 ms       20 ms

These are one paired replay on one GPU, with Java-phase and browser-frame
clocks recorded separately. Frame gaps measure browser presentation
intervals. Both runs briefly activated the loading cover at both
crossings. The matching triangle and chunk counts and successful route
validate the narrow experiment. They do not establish pixel parity or
cover interactions, rapid reversals, teleports, or level changes in Firefox.
Keep the prototype private. The next experiment should split the first
bridge cost into dynamic scenery repacks, actor submission, lighting masks,
and Worker waits, then prepare eligible products while the current scene
is still active. Preserve the regular server authority and frame safety gates.
Evidence is under output/diagnostics/browser-overlapping-handoff/ in the
worker checkout.

Work to test
------------

1. Region loading. Compare cold and warm crossings and return trips in both
   clients. Time terrain preparation, scenery transforms, mesh packing, GPU
   upload, and the gap until the next playable frame. Reuse the existing
   preload and bounded residency paths. Let the measurements decide whether
   to reduce rebuilds, change upload scheduling, or cache more regional data.

2. Rendering cost. Prototype vertex reuse in one area. Share vertices only
   when all submitted attributes match, and preserve index order and material
   batches. Measure upload bytes, resident geometry, CPU packing, and GPU
   frame time. Time the main draw and shadow passes separately. Compare a
   busy scene at normal zoom and wide zoom with matching settings.

3. Tile geometry. Resolve the diagonal and surface on each half, wall
   endpoints, and roof coverage from the same tile description. Preserve
   automatic matching for existing maps and allow editor overrides where
   matching is ambiguous. Compare both clients on diagonal buildings,
   mixed floors, slopes, shorelines, and upper and underground levels.
   Keep collision, picking, and pathing behavior intact.

Use the same route, map, camera, and graphics settings on each A/B run.
Record steady frame time, worst gaps at crossings, and visual parity
before adopting a change. Record the result even if a prototype stays off.
