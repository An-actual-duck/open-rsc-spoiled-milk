Terrain rendering and world loading plan
=======================================

Improve terrain consistency, travel, and rendering headroom in the browser
and standalone clients. Start with a measured region-crossing route and a
small vertex-reuse prototype. Keep the tile map as the source of truth.

Evidence
--------

The v0.3.25 browser audit covered all 1,400 static geometry chunks. Within
each chunk, sharing byte-identical vertices preserved every indexed attribute
and triangle order. With 32-bit indices, estimated vertex and index storage
fell 29.17% for terrain, walls, and roofs, 17.60% for static scenery, and
about 21.5% across the catalogue. The audit measured geometry bytes. Travel time,
GPU memory in use, and FPS still need an in-game comparison.
Evidence lives under output/diagnostics/terrain-pipeline-audit/v0325/.

Private persistent overworld experiment
--------------------------------------

The private full-residency mode uploads the whole compact overworld
catalogue at entry. A persistent static terrain selection derives its
window from the absolute camera position. The same resident geometry
identities survive camera travel and changes to the gameplay region
origin. When walking, scenery retains the authoritative rows for
live and changed objects. The production renderer keeps its default
bounded policy.

The detached camera demonstration selects authored terrain and
scenery directly from the resident catalogue. The test account stays
put. The flyover omits actors and local lighting masks. The matching
walking mode retains actors, normal lighting and gameplay authority.

On one matched walking route both modes held all 1,400 catalogue
entries, with 988,074,828 bytes of resident geometry. The layout with
the original region selection paused for 526 ms outbound and 286 ms
on return. Camera-based terrain selection measured 495 ms and 341 ms.
Both sent real region transitions for the gameplay scene. The test
therefore leaves the gameplay transition on the path to a new frame.
The full-residency login still requires checked CPU and graphics
readiness, with no bounded residency gate when full mode is selected.

The 20-second flyover replay crossed two old boundaries while the
player position and gameplay scene epoch stayed fixed. All 1,400
geometry entries stayed resident, with zero additional catalogue
downloads. The sampled boundary frame intervals were 22 and 24 ms.
The renderer continued to report ordinary uploads outside the static
catalogue. The replay and comparison are under output/diagnostics/
browser-persistent-world/ in the worker checkout.

Live walking handoff
--------------------

A Firefox replay on the private world walked across the boundary near
(144, 644, 0) in both directions using the same map, options, and route.
The server reached the same waypoints in both runs. Both held all 1,400
catalogue entries and downloaded zero new catalogue bytes during travel.

The prepared walking prototype keeps the active scene until authoritative
player and static receipts finish. Same-scope global level 0 walking can
release the first assembled frame once it has the current immutable
prepared terrain, matching scenery revision and origin, and no pending
terrain presentation product. Other transitions keep the two-sample
stability check. WebGL still waits for the scene's required geometry.
The prototype is opt-in with preparedwalk=on in private full-residency mode.

                                    Existing   Prepared walk
  Fresh frame gap, outbound           512 ms      480 ms
  Fresh frame gap, return             286 ms      284 ms
  Receipts to Java release, outbound  180 ms      141 ms
  Receipts to Java release, return    106 ms       92 ms
  First full WebGL bridge, outbound   138 ms      146 ms
  First full WebGL bridge, return     114 ms      120 ms
  Stationary frame median              20 ms       20 ms

These are one paired replay on one GPU, with Java-phase and browser-frame
clocks recorded separately. Frame gaps measure browser presentation
intervals. Both runs briefly activated the loading cover at both
crossings. The matching triangle and chunk counts and successful route
validate the narrow experiment. They do not establish pixel parity or
cover interactions, rapid reversals, teleports, or level changes in Firefox.
Keep the prototype private. The next experiment should split the first
bridge cost into dynamic scenery repacks, actor submission, lighting masks,
and Worker waits, then prepare eligible products while the current scene
is still active. Preserve the regular server authority and frame safety gates.
Evidence is under output/diagnostics/browser-overlapping-handoff/ in the
worker checkout.

Terrain relief preparation during travel
----------------------------------------

The private terrainlookahead option prepares neighbouring overworld
relief masks on a background worker. It reuses a mask only when the live
plane, signed level, absolute bounds and every height sample match. A
mismatch uses the normal builder. The cache holds up to six masks. GPU
residency and the authoritative scene handoff use the same settings as
the control.

On one controlled Firefox replay, the mask matched at both crossings.
Outbound lighting fell from 122 to 44 ms, and the fresh-frame gap from
463 to 395 ms. On return, lighting fell from 105 to 17 ms, and the gap
from 289 to 187 ms. Both runs reached the same server destinations and
still briefly activated the loading cover. The full first submission
fell from 135 to 57 ms outbound and from 116 to 27 ms on return.
The results are in output/diagnostics/browser-overlapping-handoff/
lighting-comparison.json in the worker checkout.

Next keep ordinary movement presentation active during the remaining
handoff. Time the authoritative receipts and first scene assembly
separately from the bridge. Check whether live object reconciliation
or actor rebasing holds that first frame. Use the normal loading path
for floor changes and teleports.

Ordinary walking notice and scene assembly trace
-----------------------------------------------

The private quietwalk option delays the ordinary streaming notice by
500 ms after a previously ready scene. It keeps the previous scene
visible and keeps the normal click gate until the authoritative new
scene is ready. Hard transitions, startup and errors still show a
notice immediately. A prolonged ordinary transition still gets a notice.

Both crossings in one private Firefox replay kept the notice hidden
while the click gate closed and reopened. Fresh-frame pauses were
426 and 188 ms. This pass targets the visible notice and measures the
remaining freeze. It does not provide continuous camera or actor frames.

The first new Java frame spent 60 and 54 ms in scene rendering and
82 and 17 ms in resident scenery assembly. Scene setup was 2 ms on
each crossing and HUD/overlay work was 1 ms. The return click landed
one tile away from the earlier replay endpoint. Evidence is in
output/diagnostics/browser-overlapping-handoff/quiet/walking-notice-and-cpu.json.

Move scene render preparation and exact static scenery reconciliation
forward on the old scene's timeline. Profile the individual render phases and reuse checks before adding
workers. Keep contact,
picking and server receipts bound to the authoritative scene.

Early visual submission attempt
-------------------------------

The private livewalk experiment allows a visual frame during an ordinary
same-scope surface handoff after the player receipt and complete prepared
terrain are available. It verifies renderer coverage, leaves the static
scene receipt and picking gates in place, and gives the browser no reason
to mark a provisional frame authoritative. The reference game/UI path
still assembles the frame.

In a private Firefox replay the server player receipt arrived at 12 and
9 ms from context entry. Both receipts were complete at 111 and 66 ms,
and the first scene assembly started at 126 and 78 ms. The attempted
overlap produced zero intervening visual frames. The freshness gaps
were 426 and 180 ms. This prototype did not improve ordinary movement.
Evidence is in output/diagnostics/browser-overlapping-handoff/live/
handoff-result.json.

The next design should give the render worker an independently replayable
committed scene, with origin, terrain/object draw references and camera and
actor positions captured before transition. Establish buffer ownership and
independent cadence first, then feed confirmed motion in world coordinates
and measure the actual Worker frame times while the Java build is blocked.
Keep the interactive scene on its normal authority and readiness path.
Avoid treating a retained screenshot or deferred notice as motion proof.

Independent render worker replay
-------------------------------

The private workerreplay option lets the worker retain the last complete
global level 0 view's draw list, matrices and uniforms. The worker owns
these arrays after returning the Java transport buffers. It redraws the
resident scenery, existing sprite batch, sky and UI coverage without a new
Java frame. An ordinary transition reaches the worker in its own packet.
A new layout or command that can mutate renderer resources stops replay
before the worker applies it. Replay has a 500 ms time limit and uses no
new authority or input path.

A Firefox replay submitted 15 worker redraws outbound and 10 on return.
The longest measured start-to-start interval within replay was 18 ms.
That timer statistic excludes the gap from the last replay draw to the
new Java scene and does not measure browser scanout. The Java frame
gaps were 407 and 220 ms. Camera and actors kept their committed poses,
so visual movement continuity has not yet been achieved. Evidence is in
output/diagnostics/browser-overlapping-handoff/worker-replay/replay-result.json.

The next step is to pass bounded, confirmed movement in world coordinates
to the worker. Reproject static scenery and actor anchors from a shared
camera pose. A local actor may move along a confirmed segment. Avoid
advancing past it or playing a segment after a reversal or scope change.
The final handoff also needs a safe lifetime for the old GPU resources
until the new scene is committed, since the current replay stops as
soon as scene updates can mutate those resources.

Confirmed movement in the worker
--------------------------------

The private worker replay receives the accepted surface context's packed
player destination in world units. Each committed frame labels the local
player sprite and stores its rendered world position. The worker moves from
that position toward the confirmed destination with an upper bound of four
tiles, never passing the destination. The same camera translation projects
terrain, scenery and the other actor sprites; the local sprite moves with
the camera. It uses the previously captured sprite image, height, lighting
masks and UI. The server still controls movement and interaction.

The private Firefox route drew 16 outbound and 8 return worker frames
with a movement transform. Draws were spaced at most 18 ms apart within
the replay window, excluding the end of replay through the next Java
frame. Gaps between Java submissions were 422 and 181 ms. Both routes
crossed successfully with no new catalogue downloads or visible notice.
No claim of continuous movement through the entire handoff, sprite
animation parity, floor or teleport behavior, or scanout is made.
Evidence is in output/diagnostics/browser-overlapping-handoff/
worker-motion/motion-result.json.

Next measure the tail from the final moving worker frame to the first
replacement frame. Give the renderer separate lifetimes for the committed
and incoming sprite atlas, lighting masks, and changed local geometry.
Reconcile the two poses on commit and test reversals and steep terrain
before adopting the experiment.

Keep old resources through frame planning
-----------------------------------------

The private walkbuffer option leaves the committed scene's GPU resources
available through sprite planning and intermediate holds. The worker
copies incoming mesh and texture updates into a queue of at most 128
commands and 16 MiB. It applies them in packet order when the replacement
frame is submitted. A new layout, superseding transition or budget refusal
ends the overlap and uses the ordinary update path. There is no extra
copy of the old whole-world GPU catalogue. The protocol and renderer
readiness checks continue to control the new interactive scene.

On the matched private Firefox route the gap from the last worker redraw
that applied the motion transform to the first replacement frame fell
from 158 to 35 ms outbound and from 31 to 17 ms on return. Worker redraw
counts rose from 17 to 22 and from 9 to 11. The queue delayed 21 resource
commands outbound and five on return, peaking at 11,414,884 bytes.
Server destinations matched and ordinary crossings showed no notice.
The Java submission gaps were 457/187 ms without staging and 417/209 ms
with staging. These numbers measure submission intervals. They cannot
detect how long the worker has held at its confirmed movement endpoint.

Check endpoint dwell and pose reconciliation separately, then repeat on
turnarounds and sloped terrain. Evidence is in output/diagnostics/
browser-overlapping-handoff/walk-buffer-comparison.json.

Walking pose correction and graphics backpressure
------------------------------------------------

Player testing reported a backward snap and a severe perceived slowdown
despite the shorter worker-to-Java submission interval. That interval
can include repeated poses and says nothing about the direction of the
replacement pose. The private walkstabilize option skips duplicate
worker poses and limits replay to one outstanding GPU draw. A bounded
visual correction holds a small forward lead during Java catch-up, blends
from the last visible camera and ends on timeout, reversal or scope loss.

The candidate's first raw Java pose was about 114 and 92 world units
behind its last worker pose, with 128 units per tile. The correction
reduced the backward component along travel to zero on those first
submissions. Intervals from the last distinct worker pose to the
replacement were 29 and 15 ms. Java submission gaps were still 408 and
225 ms. There were no busy-GPU or identical-pose skips on this run, and
the return ended two Y tiles from the previous route endpoint. A very
slow browser startup timed out once and was retried separately.
This remains a private preview. Reproduce the frame-rate drop under
the player's camera and window settings before claiming it is fixed.

Evidence is in output/diagnostics/browser-overlapping-handoff/
stabilized/stabilization-result.json.

Visual review of worker replay
------------------------------

The player's review of the stabilized Firefox preview reported a visible
backward correction, frozen player animation, and a sustained FPS drop.
The preview request included walkbuffer and walkstabilize and fetched the
matching renderer. The previous automated result covered just the first
replacement pose's forward component in a separate replay.

Worker replay still draws the same composed character sprite for the
whole overlap. The correction holds a forward offset and eases it out.
If Java's next positions are still behind when the offset decays, the
character can visibly move back after the first replacement frame.
The worker busy-draw guard limits replay submissions; Java scene assembly,
resource promotion, and the next several frames can still hitch.

Keep the replay experiment private and treat the current build as a failed
visual review. Measure the local character's displayed positions and sprite
changes through replay and the next second of ordinary rendering. Record
the full run of frame intervals and the player's display and camera settings.
Require preserved walking animation, no unintended backward step or camera
jump, and no sustained cadence drop on ordinary walking before promoting
this path. The normal authority path remains the comparison. A next
candidate should advance the local animation and use one shared visual
movement timeline through the handoff, including release of any correction.

Optional streaming policy
-------------------------

Keep the current loading mode as the default. Develop an opt-in mode that
keeps a wider buffer of prepared world data in RAM and gives nearby GPU
geometry more room to stay resident. Treat whole-overworld GPU residency
as an upper-bound test. The compact private replay held about 942 MiB of
geometry alone, plus textures, shadows and driver overhead. Measure login
time, peak memory and crossings together before choosing a player budget.

The private profiler preserves the first full Java submission per recent
scene epoch. A replay measured 122 of 135 ms outbound and 105 of 116 ms
on return inside lighting preparation and submission. Geometry took 7 and
2 ms respectively. These are Java bridge measurements, including calls
to submit lighting, and do not measure GPU execution. Split terrain relief,
glow and roof-mask work next, and reuse the verified walk-ahead terrain
mask test where the inputs match. Evidence is in
output/diagnostics/browser-overlapping-handoff/profile/first-crossing-frames.json.

Index static scenery by where it belongs. Preload along actual travel and
keep the recently visited area available for reversals. Refresh live
actors, changed objects and collision from the server-authoritative
scene. Present the current scene through preparation and publish the
incoming one once its matching render products are ready. Keep separate
coverage for crossing, reversing at the boundary, interacting during a
crossing, changing floors and reconnecting after graphics context loss.

Work to test
------------

1. Region loading. Compare cold and warm crossings and return trips in both
   clients. Time terrain preparation, scenery transforms, mesh packing, GPU
   upload, and the gap until the next playable frame. Reuse the existing
   preload and bounded residency paths. Let the measurements decide whether
   to reduce rebuilds, change upload scheduling, or cache more regional data.

2. Rendering cost. Prototype vertex reuse in one area. Share vertices only
   when all submitted attributes match, and preserve index order and material
   batches. Measure upload bytes, resident geometry, CPU packing, and GPU
   frame time. Time the main draw and shadow passes separately. Compare a
   busy scene at normal zoom and wide zoom with matching settings.

3. Tile geometry. Resolve the diagonal and surface on each half, wall
   endpoints, and roof coverage from the same tile description. Preserve
   automatic matching for existing maps and allow editor overrides where
   matching is ambiguous. Compare both clients on diagonal buildings,
   mixed floors, slopes, shorelines, and upper and underground levels.
   Keep collision, picking, and pathing behavior intact.

Use the same route, map, camera, and graphics settings on each A/B run.
Record steady frame time, worst gaps at crossings, and visual parity
before adopting a change. Record the result even if a prototype stays off.
