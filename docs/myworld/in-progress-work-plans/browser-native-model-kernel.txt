Private browser-native model transform kernel
=============================================

Scope and ownership
-------------------
This is a default-OFF private experiment, not an adopted performance improvement.
It moves only RSModel.rotate1024's numeric vertex loop from CheerpJ-generated
Java code into an explicit JavaScript Int32Array kernel. The Java caller still
owns model-transform refresh, world bounds/frustum decisions, trigonometry table
lookups, visibility, face processing, picking and exception wrapping. The
existing Java loop remains literally unchanged as the default and fallback.
No gameplay, camera rules, geometry, shaders, shadows, artwork or native desktop
renderer defaults change. No server or public deployment is part of this task.

Rationale
---------
The manager's live Firefox combat CPU sample found a generated function whose
current-session body structurally matches RSModel.rotate1024, accounting for
about13% of deepest-JS samples in two20-second diagnostic windows. That is
motivation for a targeted native kernel, not proof of an achievable FPS gain.
The JavaScript loop uses Math.imul for wrapping32-bit products, signed shifts
and truncation to match Java integer arithmetic. Source and output arrays are
borrowed in the native call, consumed inline, and never retained.

CheerpJ's current interop documentation states int[] and Int32Array are passed
by reference: https://cheerpj.com/interoperability/
Native callbacks may return a value or Promise:
https://cheerpj.com/docs/guides/implementing-native-methods.html
Our new callback returns a synchronous boolean because its entire operation is
local numeric work. It does not adopt the separate global sync-dispatch
experiment or alter existing native callbacks. Actual browser JNI writeback
must be verified, not inferred solely from these documents or CPU tests.

Private controls and receipts
-----------------------------
Only WebGL benchmark URLs parse modelkernel=on/off; default off. Ordinary and
software URLs do not add the property. The opt-in property is
spoiledmilk.browserNativeModelKernel. BrowserBootstrap explicitly installs
BrowserNativeModelKernel only when both the benchmark and kernel properties
are true. Property-only desktop startup still uses the original Java loop.

browserProof.privatePolicies.nativeModelKernel reports requested/available/
enabled from the actual Java getter. An old client JAR without the helper is
reported unavailable; requesting ON fails rather than pretending it is enabled.
browserProof.nativeModelKernelWork reports actual native attempts, successful
calls, vertices and rejections. Enabled without successful calls is not proof
that the kernel ran. No new hot-loop timers or browser polling are introduced.

Fallback and failure boundaries
-------------------------------
Java checks positive vertex count and near plane, every input/output length,
nulls and all output/source or output/output identity aliases before JNI.
JavaScript validates Int32Array representation, scalar int ranges and shared
ArrayBuffer overlap before any write. Source/source aliases are supported.
Unsupported inputs return false and execute the literal Java loop. Nonpositive
near planes deliberately retain Java behavior, including possible division by
zero and partial writes. Positive near planes guarantee a nonzero divisor in
the division branch. Malformed trig indices still fail in the unchanged Java
setup before the native branch. Backend errors are not assumed to become Java
Throwable instances; no fake Java catch/recovery contract is claimed.
