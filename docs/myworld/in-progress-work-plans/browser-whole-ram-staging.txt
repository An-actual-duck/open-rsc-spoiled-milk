Private full-overworld system-RAM delivery and staging
===================================================

This experiment is default OFF. wholeram=on requires the existing private
wholezone=on, renderworker=on, benchmark WebGL coverage path with overlay delta
OFF. Same-thread browser and desktop choices remain unchanged. This frontend
and tooling work does not itself establish useful RAM residency or performance.

Source delivery
---------------

1797 files, 46,101,718 payload bytes, 46,101,734 bytes including the header.
The package fingerprint is

Canonical paths, contiguous offsets, all payload hashes, signed levels, world
spaces and exact typed metadata are cross-checked against that manifest. All
source is retained, including non-overworld dependencies; prepared useful data

The at-most-4 MiB index binds the exact client JAR, GPU catalog, four packing

incomplete. Complete preparation additionally requires a hash-bound WRP1 file
(maximum 1536 MiB), 445 L0 activation recipes and 1330 query cells for levels
0/1/2, a hidden-roof option binding, and positive prepared primitive storage.
Java owns WRP1 interpretation and validates/installs the immutable provider;
the Python validator proves delivery membership, bounds and hashes, not the
semantic correctness of prepared pages/model templates.

Tools
-----
- tools/browser-gameplay/whole-ram/source_bundle.py builds/validates raw source.
- tools/browser-gameplay/whole-ram/bake.py launches one bounded headless CPU
  baker from the exact clean-source JAR. A full cook is manager-only on the
  integrated artifact commit and requires its matching complete GPU catalog.
  It never substitutes classes or rebinds an old catalog to a new JAR.
- scripts/browser-gameplay/prepare-whole-ram-client.py first requires the full
  successful RAM receipt, matching GPU/client/settings/assets and exact files.
  It prepares a NEW client stage without starting any service. RAM files are
  listed only in bootstrap-whole-ram-files.txt; the ordinary bootstrap is byte
  unchanged and RAM OFF never copies/opens that list. The three files are
  linked when possible, otherwise copied and hash checked.

The stager emits urlOn/urlOff with wholezone=on in BOTH and the same accepted
private quality/optimization settings. Only wholeram changes. Files and stage
receipts are declaration evidence, not runtime readiness.

Readiness and memory
--------------------
Proof names are privatePolicies.wholeRam, wholeRamRequested,
wholeRamDelivery, wholeRamJava and wholeRamResidency. The bounded 18-word Java
receipt allows progress (zero counters before initialization, then full source
with preparedReady=false). It requires exact full counts before preparedReady.
The final primitive ledger must equal prepared.retainedPrimitiveBytes plus the
46,101,734-byte source array. Split counters preserve unsigned low words.
These are primitive-storage counts, excluding Java object headers, CheerpJ/VM,
filesystem copies, temporary startup data, driver memory and process RSS.

The initial LOGIN stays usable while initialization waits for a world/GPU
catalog. WORLD loading remains covered until useful prepared Java data is
ready. GPU readiness is separately tied to the exact same catalog; staged raw
source or a GPU ready flag alone cannot claim CPU prepared readiness. Failed
receipt validation clears CPU flags and blocks world presentation; disposal
clears them too. Java independently owns atomic provider readiness and recovery.

- tests/myworld/test-browser-whole-ram.mjs: private policy dependencies, bounded
  pending/source/prepared receipts, byte counters and malformed metadata.
- tests/myworld/test-browser-whole-ram-staging.py: conditional delivery and
  early refusal of incomplete/pilot data, wrong artifacts and non-integrated
  full cooks, using explicitly non-executable synthetic test data.
- node --experimental-vm-modules tests/myworld/test-browser-webgl-frontend.mjs
  and --whole-ram: actual frontend mocked native/DOM path, usable LOGIN,
  source-only WORLD cover and complete-ready release, plus inherited ordinary
  input/layout/error/disposal contracts. No hardware proof is claimed.
- Independent ai3 source delivery and Java prepared-data correctness tests are
  separate evidence. The complete CPU capacity cook can validate this format
  even when explicitly bound to an old GPU reference for CPU-only testing;
  such data cannot be staged against a fresh artifact.

Actual integrated fresh-source build/GPU bake/RAM cook, Firefox JNI readiness,
continuous walking and measured performance/memory remain manager-owned gates.
No browser, GPU, server, public deployment or release action is performed here.

Stopped-session receipt correction
----------------------------------
The first actual RAM startup exposed a parent receipt ordering issue: finish
published readiness before dispose cleared the child, while postMessage had
already cloned the proof. Disposal now clears CPU source/prepared flags and
combined GPU readiness, marks the proof stopped/disposed, and sends the final
proof after cleanup before the stop event. Direct external disposal uses the
same idempotent path. Readiness has no live-session meaning after disposal.

The actual frontend fixture now structured-clones every parent postMessage.
Its RAM test resolves Java exit after ready, checks the final cloned parent
receipt has all readiness false, verifies the earlier clone remains ready,
and checks final proof precedes stop. Ordinary mocked frontend also passes.
This fixes observability only; it does not diagnose the separate Java prepared
decode startup exit and makes no new runtime/memory/performance claim.

Explicit roof-variant cook option
---------------------------------
Actual startup rejected visible-roof CPU products for a hidden-roof client.
The driver now accepts --hidden-roofs (default false) and forwards ONLY the
offline property spoiledmilk.browserWholeRamCookHiddenRoofs=true|false. It
does not change a running client preference or rewrite any cooked header.
The receipt records the Boolean, the returned prepared.hiddenRoofs must match
the request, and the stager requires receipt/product option agreement. Existing
frontend config already includes the cooked option. Each variant therefore
requires its own real cook. The headless CPU timeout is bounded to 300 seconds.

The expanded staging/refusal fixture passes 24 checks, including both explicit
offline properties, wrong option types and --hidden-roofs reaching the genuine
missing-baker refusal before execution. The 37 policy/receipt checks also pass.
No Java cook, client, browser, GPU or server was run for this driver follow-up.
