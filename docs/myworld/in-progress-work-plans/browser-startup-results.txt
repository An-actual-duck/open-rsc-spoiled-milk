Outcome
-------
The former pre-client delay was dominated by 2111 serial HTTP-backed RAM reads.
The public transport now downloads exactly three bounded, hash-verified files,
then copies from flat session-owned /str inputs to the original /files paths.
Temporary files are unlinked after Java closes streams. Canonical data, map,
client core classes, source/recipe/readiness checks and private transport remain
unchanged. The outer page now displays actual startup stages, file/byte progress
and Cancel rather than leaving a static Starting game message.

warm: 70.227 -> 16.692 seconds; peak PSS 715.8 -> 515.3 MiB; RAM requests 2111 -> 3.

Cold means a fresh isolated profile; warm is a fresh browser/Java VM reusing that
cohort's persisted profile. Start is a real Play click; the endpoint is actual
LOGIN plus at least 20 Java frames. These are Play-to-login observations, not
account-authentication or first-world timings. Each cohort is one run, so network
and runtime cache variation remain. CPU/browser startup memory is the sampled
PSS sum of that owned Firefox parent and descendants, missingPids=0 in all four
runs. It is not exact JS heap or GPU memory. No measured PSS increase occurred;
the one-payload ledger alone does not establish browser memory usage.

Follow-ups, not prerequisites
----------------------------
The ordinary 51 small files still use the existing Java transport. Persisted
verified product reuse or runtime preload may offer further savings, but this
change deliberately does not trust partial old /files outputs as a cache. Any
such reuse needs its own source-bound integrity and cross-session lifetime
review. Lower-bandwidth devices will still take longer than these PC timings.
