Whole overworld as one logical zone — architecture audit
========================================================
Dated November 11, 2026. AUDIT ONLY. Baseline source main 6d5a66a3f.
No browser/GPU/server/map/runtime changes or larger-memory defaults are approved.
The first estimate uses the upper-bound scope: the ENTIRE overworld, not a
smaller area chosen to make it fit. The owner's PC is a possible measurement
host, not an assumed deployment target or RAM/VRAM guarantee. Device system RAM
and GPU memory must be considered separately. The earlier modern-streaming plan remains saved and
planned/deferred in browser-modern-streaming-plan.txt while this audit proceeds.

Existing global L0 already shares a world-space/level coordinate namespace across
sectors. NativeLayeredTerrainSnapshot.scopeIdentity additionally includes the
current center/radius/chunk identities, so local activation still changes while
that namespace stays global. The requested one-zone experience concerns source
preparation/residency and transition behavior; simply renaming a zone does not
remove the existing work or authority barriers.

Three proposals that must not be conflated
-----------------------------------------
A. One continuous logical L0 zone, internally streamed. Gameplay and visual source
   identities need not reset on each 48-tile border; local collision/pick/interest
   windows, origin rebasing and GPU page residency may remain bounded internals.
   This is a user-visible continuity goal, not a requirement to draw everything.
B. The whole zone ready in system RAM. Specify whether this means compressed
   terrain/source records, decoded tiles/collision, canonical geometry, CPU
   picking models, all static objects, or all layers. Each has different memory
   and startup costs. A warm OS file cache does not equal decoded runtime residency.
C. All zone geometry resident on the GPU. This adds separate capacity, draw-list,
   culling, texture, shadow and startup-upload requirements. GPU-resident does not
   mean all geometry should be submitted, shadowed or visible each frame.

Estimate the FULL B and C proposals before substituting A or a hybrid. A may
ultimately be feasible without B or C, and full source RAM residency differs
from CPU-constructing all classic models or uploading all geometry, but these
are choices to present after the complete audit rather than automatic scope
reductions. Current limits are not an estimate of the world's actual needs.
Inventory and geometry evidence must decide what fits before implementation.

Current source constraints (source references are review anchors)
----------------------------------------------------------------
- NativeLayeredTerrainSnapshot.java:14–29,183–225 and decoder:238–270: protocol 3
  uniform pages, protocol 4 legacy 24-tile chunks, protocol 5+ 48-tile sectors;
  protocols 5–8 require radius 1/9 explicit slots, protocols 9/10 radius 2/25 slots.
  Client/server validators, query indexing, staging/readiness/atomic activation
  and acknowledgements require matching package/manifest, world-space, signed
  level, center and sequence. A giant zone is not a legal larger packet today.
  Full static source may instead be preloaded from the paired client package;
  that does not authorize activating out-of-window server state. Do not assume
  a giant network packet is necessary merely because source is cached. Any new
  whole-zone provider/catalog still needs checksums, version compatibility,
  missing cells, recovery and stale-transaction proof.
- World.java:45–78: active 3x3 sections, 144x144 local tiles, 143x143 faces, 12-tile
  model grid, 512 split-vertex limit; caches have distinct count limits (sector 256,
  CPU windows 24, terrain/wall/roof inputs 24, model products 48, prepared chunks 4).
  collisionFlags/pathFindSource/tileElevationCache and model/minimap products are
  sized/indexed to those local constants. Increasing ACTIVE_SECTION_GRID alone
  changes quadratic storage, geometry/grid counts and many algorithms; it is
  not an architectural whole-zone switch.
- mudclient.loadNextRegion and World.sectionToLocalBaseTile retain local bases
  and local-player/entity coordinates. Scene picking and classic RSModel CPU
  transforms consume these representations. RSModel.rotate1024 subtracts camera
  offsets before signed int products/shifts (current:2402 onward). That existing
  relative-coordinate pipeline can remain useful. A giant model that bypasses
  per-cell culling can still feed very distant vertices into those int products;
  do not infer that int-safe logical tile coordinates imply safe model arithmetic.
  Keep chunk origins/culling, or prove all transform/packet/index ranges after
  a global-coordinate refactor. One logical zone does not require one huge mesh.
- BrowserWebGLBridge.java:21/51/181/319/419: max 256 active draw chunks, 512 resident
  chunk identities, 224MiB Java-side GPU chunk residency accounting, 32768 discretionary upload
  vertices per submission and 524288 vertices per individual chunk. Each vertex
  currently contributes 28 floats/112 bytes plus triangle indices. Those budgets
  do not include the entire Java heap or all GPU ancillary resources. CachedChunk
  holds metadata rather than retained interleaved vertex arrays: do not count
  this 224MiB accounting as an additional actual CPU allocation. Canonical CPU
  geometry, temporary packing and Worker-owned copies need separate estimates.
- webgl.js:27/67/71/131/140/191: 512 resident chunks, 256 active draw descriptors,
  256MiB tracked chunk/texture GPU budget, bounded indices and the same 112-byte
  stride. Shadow maps, sprite atlas, overlay/retained planes, lighting masks and
  sky have separate bounded ledgers; driver/program overhead is not accounted
  for by the chunk counter. Color/shadow culling must remain independent of a
  zone's logical extent; one giant mesh would undermine useful cell culling.
- browser-render-worker-protocol.js and transport: 64MiB packet cap, bounded
  command count, two in-flight packets and one producer batch; 16MiB owned return
  pool. A full world cannot be handed to the Worker as one unbounded array or
  transferred while Java retains a borrowed view. Static resource lifetimes,
  disposal, source epochs and delayed ACK failures still apply.
- Server RegionManager.java:127 and LayeredSpatialEntityIndex.requireBoundedWindow:
  per-owner interest membership is bounded (4096 region cap). Player visibility
  still uses scoped logical windows and range filtering. Static map preloading
  must not subscribe every player to all NPCs/players/items/scenery updates or
  expand combat targeting/collision authority to an entire zone. The 4096 cap is
  not itself proof the selected 445-cell map cannot fit; interest-window size and
  range/entity/packet semantics are separate constraints. Audit packet
  coordinate/delta widths, local lists and entity capacities before changing
  interest semantics. Keeping bounded dynamic interests is compatible with A.
- World.setLayeredTerrainScope:316 onward currently changes scope revisions,
  prebuilds and cached active/predictive/symmetric products. Immutable storage
  keys and mutable activation epochs cannot be casually merged. A zone-wide
  identity must still invalidate the exact affected products after scenery,
  doors, terrain/definition or material mutations, and reject stale asynchronous
  output. All layers/world spaces must remain distinct during reuse.
- World.java:2605–2640 explicitly builds stacked upper-floor walls/roofs from the
  completed roof elevations below. Active-floor-local and ground-view stacked
  products are deliberately different; sharing their key flattens upper stories.
  A logical L0 zone needs its visible upper/roof dependencies inventoried even
  if those upper floors are separate gameplay zones. Ground tiles alone do not
  account for all pixels, shadows, indoor roof masks, picks or authored scenery.

Audit outputs required before choosing an architecture
-----------------------------------------------------
1. Exact paired source-selected package identity and hashes, L0 storage-cell
   roster/bounds/holes, placement count/type/model and all visible L1+ dependencies.
   Exclude underground/world spaces only when explicitly outside this proposal;
   preserve unknown/unresolved objects as findings, not zero cost.
2. Separate disk/compressed, decoded canonical terrain, CPU classic-model/picking,
   canonical GPU geometry, packed GPU vertex/index, texture/atlas/shadow and
   transient-copy costs. Do not multiply one unrepresentative cell or confuse
   server object definitions with active client vertex payloads.
3. Enumerate every hard local-window/protocol/index/capacity dependency above and
   classify: can stay bounded internal, needs an interface refactor, or genuinely
   requires global resizing. Identify client/server/tooling compatibility and
   legacy/native renderer defaults separately.
4. First-login/download/preparation cost, long-route mutation/staleness handling,
   retained ready authority and memory exhaustion/context-loss behavior. The
   proposal must quantify upfront download/zone-entry preparation versus later
   walking smoothness. The owner may accept a substantial initial wait in
   exchange for uninterrupted travel; do not rule that tradeoff out implicitly.
   Report later GC spikes and incomplete-geometry behavior separately.
5. Recommend A/B/C separately for entire-overworld scope and stated device
   RAM/VRAM classes, with explicit unmeasured parts,
   required source changes and confidence. This audit makes no FPS, startup-time,
   RAM-fit or full-GPU-residency promise. Measured data decides the next task.

Final audit recommendation — no implementation yet
--------------------------------------------------
Full overworld scope is a plausible next private prototype on the measured host's
capacity: the measured current-copy mesh subtotal (~2.05GiB before extras) leaves
apparent capacity headroom under the reported 12GiB dedicated VRAM, and primitive
CPU lower bounds are materially below total system RAM. These are reasons to
TEST full B/C, not memory-fit/FPS/startup guarantees. Current software policies
would reject the workload long before that hardware limit.

A: Continuous logical-zone behavior remains the experience goal. The global L0
namespace already exists; preserve bounded dynamic interests/local authority and
local-coordinate working sets where useful. This alone neither requires nor
proves B/C and must not be used to silently shrink the requested whole-zone audit.
B: Bulk immutable source residency is modest by file bytes; full prepared CPU
geometry is much larger. Specify exactly what stays resident, model/header/cache
peaks and the browser/CheerpJ ownership and heap limits. Deliberate package
delivery/hash/version/dynamic-overlay invalidation must be designed; current
browser staging does not already deliver all sector payloads.
C: Full current-copy GPU residency is capacity-plausible on this host, with extra
resource allowances. It needs a separate global residency catalog and bounded
visible draw/pick/shadow working sets, not every model submitted every frame.
The current 256 active/512 resident limits, budgets and readiness assumptions
need deliberate redesign. A monolithic mesh or simply raising CHUNK limits does
not solve source construction, picking, local collision or dynamic invalidation.

If the owner chooses this direction after the audit, write a focused prototype
contract before changing runtime code. It must define global cell/source keys,
new browser source delivery, local-origin transforms, dynamic scenery/door/model
revision overlays, immutable ownership, bounded initial uploads and memory peaks,
visible lists, upper/roof state, stale results and context-loss rebuild. Measure
actual browser allocation/headroom, upfront download/decode/prepare/upload wait,
GC, walking/camera/interaction latency and completed frames. The owner may choose
a long initial zone-entry wait to eliminate later loading; present that measured
tradeoff plainly. Do not declare it unacceptable or promise it will be short.

Earlier immutable-cell reuse/cache/prepare-ahead/background/offline/compact-format
plans remain saved in browser-modern-streaming-plan.txt, not rejected. They may
be used within a chosen zone design later, after the full-scope comparison and
owner decision. This audit does not adopt any candidate, change defaults, edit
the map, activate a server or authorize a public release.
