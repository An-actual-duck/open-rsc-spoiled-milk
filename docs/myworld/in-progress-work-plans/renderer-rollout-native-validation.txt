Renderer rollout native combat and lifecycle validation
======================================================

Scope
The owner approved the accepted renderer visually and requested all remaining
pre-rollout checks except the 30–60 minute soak. This task changes optional
benchmark/test tooling only. Production renderer, gameplay, network authority,
assets and map files are unchanged. Oracle and the original browser fixture
are untouched. All native runs use disposable loopback databases/accounts.

Production implementation baseline: 8385412ee48047efc6fe8d30a2eca8972b178a8a.

Root verifies every packaged class matches the approved baseline. Each native

compiled test helper digests, runtime and actual GL vendor/renderer/version.
The test helper source may advance independently of unchanged client classes.

Actual combat workload
The new combat-real phase disables the old visual-only projectile generator.
Six ordinary production channels run together: Ice Crystal, Thunder Strike,
Battering Ram, bow/arrows, tin shuriken and melee, with production bear summons
assisting. Actors receive survival HP so deaths do not prematurely stop the
short workload. No map collision is edited: casters use authored walkable tiles
adjacent to their targets. There are 16 controlled players, 32 controlled NPCs
and eight requested bears. The viewer authenticates normally and receives the
ordinary scene/combat packets.

Admission is not accepted as proof of damage. The private observer reads each
NPC's factual typed contribution ledger on the server game thread, attributing
positive damage separately to all six casters/channels. Resource consumption,
NPC HP changes, active summon combat events, client received projectiles,
active floating hit splats and elemental effect playback are retained too.
Report validation rejects missing damage contributions/resources, no active
summon events, no received splats or no overlapping received projectiles.
Summon contribution credit remains zero in this fixture despite active combat
events. Thus this is summon animation/engagement stress, not proof of successful
summon damage attribution or a change to summon reward/credit behavior.

Window and lifecycle coverage
The independent RendererWindowLifecycleGpuFixture owns its GLFW context/thread
and briefly creates its own native window, never input callbacks or grabs. It
checks real1100x700 resize, windowed/fullscreen/borderless transitions, minimize,
restore/activation, settings serializer roundtrip and idempotent destruction.
X11 restore alone did not activate the minimized window; explicit own-window
show/focus models user activation and passed. This is Linux WM behavior and is
not reported as a production defect.

The full-game visible lifecycle phase requests window modes through production
settings, applied by the renderer thread. Resize/minimize/map/activate use
xdotool targeted to the unique visible XID of the exact current fixture PID;
each operation rechecks PID ownership. It sends no synthetic keys and installs
no new callbacks or grabs. Recorded native sizes/flags and completed-render
counters show the world continues/resumes. Fullscreen modes can auto-minimize
when focus is lost; this is retained, not called visible acceptance of every
frame. The final windowed restore must be visible and uniconified.

The same phase cycles Off/Low/High repeatedly, performs same-position/area/
level2/back teleports, then ordinary server logout confirmation packets and
normal authentication twice in the same client JVM. It saves the final Low
preference through the actual production SettingsStore and verifies the file.
Deliberate window changes, Off periods, loading and login waits make this a
functional lifecycle test, not a steady-FPS acceptance cohort. GPU query timer
lifetimes can reset at relog, so combined lifecycle GPU timing is omitted.

Preserved negative probes
All earlier runs and failed test data remain under declared test output roots.
Initial combat smoke exposed caster LOS placement, corrected by choosing
adjacent authored tiles; no gameplay changes. A compile-only prototype used a
nonexistent Equipment.getItems accessor and never ran. Native window probes
first assumed restore-without-activation and implicit settings saves; corrected
fixtures distinguish WM activation and explicit setting serialization.
The first full-game lifecycle refused an already-existing blocked spawn tile
for same-position movement. Same-position now preserves the current location;
new destinations must resolve to a nearby authored walkable tile. Actual level2
landing is near the maintained Gnome course callback, not an invented upper floor.
A direct observer-thread closeConnection probe raced the game loop and was
rejected. The accepted path uses server confirmation processed by the ordinary
client loop. A subsequent retry omitted the login admission counter normally
set by UI; corrected tooling sets it before calling the existing login method.
These harness failures do not establish owner-facing regressions.

Limits
No soak or leak-freedom claim. No live server/account/database mutation.
Native hardware/OS and additional release/package checks are coordinated by
root. Optional pending published-frame actor/roof observations can be unknown;
unknown is not zero. Received actor counts and renderer submission counters
remain distinct from visibility through scenery. Final owner visual approval
is separate from hidden throughput and scripted functional checks.

Reproduction
Prepare/start/capture/report/stop remain explicit scripts/renderer-benchmark.py
commands. Use phase combat-real with capture for short hidden throughput, and
preview --phase lifecycle --seconds50 for the visible full-game functional
sequence (Linux/X11 and xdotool required). Wait for CLIENT-DONE before report or
stop. For Java21 coverage prepend its bin directory only to the client capture
PATH and pass --gc-log; this adds universally supported -verbose:gc and retains
messages in the existing private console log. Compatibility Low can be selected
with --quality low and a scoped DRI_PRIME, verifying actual manifest renderer.
The independent native-window fixture can be compiled against the candidate JAR
and run in an isolated JVM under the shared renderer GPU flock.
