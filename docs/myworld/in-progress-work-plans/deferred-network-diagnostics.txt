Deferred network-frame diagnostics — focused client slice, 2026-11-09
==================================================================

Baseline958a278453e460d59dcfce6c102adcc42dcfc1d7.
Scope: Network_Base diagnostic guards only. No socket prefetch, protocol,
framing, timeout redesign, browser backend or server changes.

Problem
-------
The logger checked BOUNDARY_DIAGNOSTICS and its256-line cap internally, after
Java had already constructed HEADER/PROGRESS/COMPLETE/TIMEOUT/PENDING messages.
Each construction called available(). In a browser that may cross Java/JS even
when logs are disabled or their cap has already been reached. Default diagnostic
off therefore did extra socket queries, strings, and potentially diagnostic-only
I/O failures on otherwise normal packet reads.

Change
------
Each of the five call sites now checks canLogFrameDiagnostic() before evaluating
any message arguments. The logger retains its own defensive guard and the exact
existing text/line cap. The pending-attempt bookkeeping remains outside the guard
so cadence/state are unchanged. Required header/payload availability checks,
reads, partial draining, buffer growth, payload completion, timeout state and
malformed-header handling are unchanged. No other eager diagnostic sites exist
in this class; exception-context construction remains exceptional only.

Validation
----------
Actual packaged Network_Base is exercised by a same-package Scripted transport
subclass, not a replacement frame decoder. Separate JVMs test diagnostics false
and true because the setting is static-final at class initialization. The fixture
also verifies its production class origin is the packaged client JAR.

The corpus covers whole frames, partial drains before completion, resuming a
pending frame, following-frame alignment,4097-byte payload growth/draining,
120-idle-poll pending cadence, timeout state/exception, declared lengths0/1/2,
actual payload I/O failure, and100completeframes exceeding the256-line cap.
Enabled HEADER/PROGRESS/COMPLETE/PENDING/TIMEOUT strings and exact cap are checked.
The decoded corpus SHA256 must match enabled/disabled runs. A scripted
post-drain available() failure demonstrates that disabled diagnostics cannot
introduce that diagnostic-only fault; enabled behavior stays observable.

For a complete small packet, available() calls are2off vs5on before the cap.
For100packets they are200off vs456on (200protocol +256logged diagnostic queries).
After the cap, even enabled diagnostic sites avoid additional availability calls.
These are deterministic call counts, not timing, browser FPS or CPU percentages.
