# Pre-world RGB upload experiment — parked, not adopted

Decision: preserve this experiment on its topic branch and do not merge/adopt it. Main keeps the original post-world RGB upload. Java, shaders and visual quality are unchanged. Standalone `overlay.draw` keeps its immediate post-world RGB upload/check. The optional browser path validates native frame arrays and integer dimensions, uploads RGB synchronously before the existing streaming gate, and only then starts timer queries or draws shadows, sky, retained BASE, world, sprites and UI. The owned frame baseline is established after this upload. Marker-only presentation retains its old path.

`overlay.prepareRgb` requires the exact still-pending coverage declaration, validates retained capture/replay tokens without GL calls, uploads/copies the caller bytes synchronously, and stores only the internal declaration identity. A staged image cannot be overwritten, used with another declaration/dimensions or drawn twice. `begin` consumes that declaration; `drawPrepared` consumes its stage. Pure retained checks share the existing token/sequence/readiness logic; literal standalone draw/replay checks are preserved. Invalid/stale/duplicate-count/resize-incompatible retained input is rejected before touching RGB storage.

Only same-size pre-draw RGB joins the existing stream gate. Initial shader compilation, initial/resized texture storage, post-draw UI and retained capture/fade checks remain immediate. Prefix upload failures poison the whole backend even with streaming batching OFF. Batched RGB failures must reject before ANY draw, clear, retained copy or timer/query work, publish no successful frame, and block all later native or mode operations until disposal/restart. No extra C/T/retained textures are added; the combined 32 MiB peak remains unchanged.

Private controls: `?benchmark&ui-preupload=on|off`, default OFF, and `window.browserBenchmarkUiPreupload(boolean)`. Ordinary/software URLs ignore the override and expose no live switch. Pending policy changes commit only at END of the existing native `frameWork`, after streaming validation completion. Actual/presented receipts are `uiPreuploadActive`, `presentedUiPreupload`, `uiPreuploadUsed`; `worldFrameUiPreuploadPolicies` aligns with the existing world samples. Externally resetting sample arrays must reset this array too. Transitions are bounded to 64. This control cannot bypass streaming validation.

CPU tests pass: 42 OFF/ON/live frames and 568 matching effective draws/clears/copies, all fade counts 1–16, duplicate/BASE replay, resize/underground/opaque reset, exact staged token rules, synchronous borrowed-byte ownership, 32 MiB maximum-area replacement, injected RGB allocation and same-size faults with batching ON/OFF, zero draw/timer work after fault, sticky mode/native rejection, and resource cleanup. Existing scoped overlay/retained/owned-state/streaming suites and ordinary/stream/UI frontend VM variants pass. These are state/order/resource tests, not GPU pixels or FPS evidence.

The hardware preparer freezes original published JS, candidate JS, actual production world/depth shaders and native sky geometry/palettes. It requires explicit `--dependency-jar` and `--client-source-commit`. Root alone runs the isolated AMD hardware proof. The page compares original/current OFF/ON/live pixels across the same 42 cases, and injects a real invalid same-size RGB upload with batching ON/OFF to prove rejection before all world/UI/query work, sticky failure, and unchanged successful-frame counters. The manager ran frozen hardware checkpoint-v1 successfully; exact results follow.

Approved immutable dependency: manager `output/reviews/browser-display-performance/baselines/main-37a60529b/client.jar`, SHA-256 `db05079cf9ee7d5c5676f44b7f95aa6c7bdfd804dcc2527acd17f2b7486ff88b`, client source `37a60529bd2569e2832338e3770feeb699aec025`. The preceding host profile attributed about 783 ms / 20 s to RGB's post-world error poll; this experiment targets that synchronization point. No throughput gain, complete browser/device parity or 60 FPS claim follows until actual pixel/fault proof and matched runtime measurement pass.

## First gameplay comparison: inconclusive, not adopted

The initial `ui-preupload-live-1` attempt did not reach GAME: its untimed coordinate-based login left focus in the username field. This was not a renderer error. Read-only comparison found identical shared bytes in both client and Bootstrap JARs, no duplicate entries, all 50 staged Cache files identical, and unchanged display/input handlers. The existing GUI Enter transition was then verified in an untimed functional probe (647 actual world frames/ready). Product source and frozen8136 remained unchanged; failed evidence was preserved.

Manager evidence `output/reviews/browser-display-performance/benchmarks/ui-preupload-live-2/result.json` uses the corrected untimed login harness, with no input diagnostics, screenshots or profiler in timed segments. OFF totals: 2,253 fresh frames over40.2115s,56.02875 FPS,30.97825 actor groups/frame. ON:2,316 frames over40.2316s,57.56669 FPS,31.24655 groups/frame. Individual OFF/ON/OFF/ON segments are55.79175/55.77076/56.26586/59.36623 FPS. Most apparent gain occurs in the last ON segment; the first ON is effectively unchanged despite fewer actors. This is consistent with late runtime warming or variation and does not establish an isolated throughput improvement. Default remains OFF.

**GPU timer scope differs and must not be used as evidence of reduced GPU work.** The query starts after prefix RGB preupload in ON mode, while OFF mode uploads RGB later inside the timed query. Consequently the approximate2.45→2.27ms GPU decrease excludes work from the ON interval rather than proving that work was removed. Shader, triangle and texture pixel work is unchanged. JS submission starts before the prefix in both modes, but those timings alone also do not establish end-to-end gain. Successful fresh world FPS under matched plateau conditions is the acceptance measure.

A longer both-mode warmup is pending: OFF90s, ON90s, OFF20s, then four alternating30s segments. No adoption or60 FPS claim is authorized by the first paired result. This documentation update changes no source, artifact or active mode.

The earlier short pair's final ON rise was warming/variation, not adequate evidence for this optimization. GPU timer scope remains non-comparable as documented above.

**Decision: DO NOT ADOPT.** Preserve the exact topic branch, CPU fixtures, 12,976,128-byte/zero-difference actual GPU correctness proof, real-error blocking proof and both successful/failed login evidence. Do not merge the additional prefix/token/control complexity for an unproven improvement. Published main `cd219e9263ce63fe75962177922735948a59f405` keeps original post-world RGB upload. This docs-only disposition changes no source, frozen artifact, test result or public system. No60 FPS or broader-device performance claim follows from this experiment.
