Independent browser overlay rectangle review
===========================================

Scope
-----
Read-only candidate review plus independent CPU fixtures in ai2. No browser,
HTTP/game server, GPU workload or performance claim. Runtime implementation
belongs to the separate ai1 topic. This report does not approve an untested
rectangle backend; the first reviewed checkpoint only observes writer tiles
while retaining the exact row/full upload path.

Primary specification checks
----------------------------
Published Khronos WebGL2 2.0.0, section3.7.6:
https://registry.khronos.org/webgl/specs/2.0.0/#3.7.6
The current editor draft was cross-checked, without treating it as a release:
https://registry.khronos.org/webgl/specs/latest/2.0/#3.7.6
Client-array source offsets count typed elements relative to the supplied
view. Float offsets therefore count floats, not bytes. Client-array uploads
require PIXEL_UNPACK_BUFFER to be unbound; dimensions and unpack parameters
also constrain the accessible source footprint.

Khronos OpenGL ES3.0.6, section3.7.2, equations3.12–3.13 (PDF pages127–128):
https://registry.khronos.org/OpenGL/specs/es/3.0/es_spec_3.0.pdf
Row length is in pixels. Unpack alignment rounds the row byte stride, and row
and pixel skips advance the source start. Final-row trailing padding is not
read. The independent transfer oracle implements these rules for the two
actual overlay formats (RGBA/UNSIGNED_BYTE and RED/FLOAT). Its arithmetic is
separate from candidate mocks and never claims real-driver conformance.

Remaining review boundary
-------------------------
Observe-only tests do not prove rectangle planning, source strided uploads,
exact GL state restoration, both-plane upload failures, follow-on atlas/full
uploads or real browser readback parity. Those require the later stable
rectangle checkpoint and manager-owned hardware validation. Existing mocks
that ignore pixelStorei are insufficient for those semantics.

The client applies the view/element offset, then Shrink limits cpuData to the
smaller of available bytes and aligned row-stride times total rows. Queue
serialization copies that contiguous span into command storage; it does not
tightly gather the requested pixels from each row. Skipped prefix rows can
therefore be copied too. With flip/premultiply false and no PBO, the host raw
path passes the pointer and unpack state to GL without a tight CPU conversion.

A minimal borrowed subarray from the first required element through the final
required element, with srcOffset0 and skip0, bounds the submitted span. For
4-byte pixels and ROW_LENGTH=W, its byte length is
4*((rectangleHeight-1)*W+rectangleWidth). It still includes row gaps; narrow,
full-height rectangles may span almost a full plane. This is a source-based
queued-copy concern, not evidence of actual hardware bus traffic or FPS.

Agent1/root were advised to report logical texel payload, supplied view-span
bytes and measured FPS separately. No true-zero-copy claim is justified. Tight
packing or separate row calls would be a distinct reviewed experiment; no
packing implementation is authorized or silently introduced by these tests.

Packing scope revision
----------------------
After the Firefox source-span audit, the manager explicitly authorized a bounded,
synchronous JS-owned tight-packing comparison variant. This revises the earlier
no-packing prototype constraint; no earlier source/evidence was rewritten.
Required review covers both planes/geometry before allocations or GL, reusable
scratch and peak/capacity bounds, exact Float32 bits/BGRA bytes, borrowed-view
bounds and no retained Java input references. Packing has not yet been tested
against a stable candidate checkpoint, and no performance benefit is assumed.

Stable rectangle and packing review
-----------------------------------
Exact candidate923d745c0c032437f1a1f034f23b905c96c8b490 passes the expanded
independent CPU suite. Runtime is still private/default-off. The reviewed
contract permits at most8 disjoint rectangles, logical area<=60% of viewport,
and selects rectangles only with useful savings against the row/full plan.
Direct mode uses minimal borrowed strided views; packed mode uses bounded,
synchronous JS-owned scratch. Both continue using the fine writer-footprint
snapshot and original owner/ACK generation rules.

Independent results:
* 7,343 tile/ACK checks pass again against the exact rectangle checkpoint.
* 1,593,292 planner assertions across405 frames exercise104rectangle plans,
  49row plans and252full plans. The reference derives tiles per written pixel,
  then checks complete old/current union coverage, disjointness, clipped tile
  boundaries, plan caps and ACK progression without copying the grouping logic.
* 128actual-overlay/specification-model checks cover direct/packed variants
  with both scoped state and the actual owned-frame factory. Hostile row length,
  skips, alignment, PBO, flip and premultiply state is restored exactly on the
  scoped path. The explicit owner establishes canonical state initially and
  on inactive-to-active transition. Its active=false path still scopes normally.
* Minimal direct API views and tightly packed views have the expected distinct
  byte lengths. Source views have nonzero offsets; RGB starts at byte3.
* Invalid later rectangles, omitted dirty tiles and a short second plane are
  rejected before any GL call or staging growth. Failure in EITHER upload plane
  poisons the transaction; subsequent work cannot advance history. Disposal
  releases candidate resources and packing capacity in the model.
* A following full overlay upload and the ACTUAL candidate sprite-atlas module
  produce the expected texture contents, detecting leaked rectangle strides.
* Independent packing expectations preserve BGRA bytes, signedzero, signaling
  and quiet NaN Float32 payload bits via raw bytes. Tests check source isolation,
  exact element offsets, short-view bounds, no writes/allocations for bad later
  geometry, empty plans, scratch reuse, allocation failure and disposal.

Packing's12MiB retained/24MiB growth cap concerns owned scratch payload only;
it is not a ceiling on total JavaScript heap, browser command queues, driver
memory, original Java planes or externally retained test result views. The
reviewed helper retains only its scratch and numeric counters; borrowed Java
input views are consumed synchronously and not stored in owner state.
