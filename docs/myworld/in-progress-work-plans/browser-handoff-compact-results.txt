Browser handoff and compact geometry: combined private results
==============================================================

Status
------
Compact geometry has measured memory savings and passed hardware checks. The
first baseline clone reuse candidate has not established a CPU loading benefit:
its initial real ON route selected the feature but reused zero models. The next
profile/caller investigation and final warm route measurements are pending. This
document remains a draft; the CPU optimization is not accepted as complete.
No public server, public client default or player map was changed by this work.

What changed
------------
1. Compact geometry gives the private catalogue a 48-byte vertex layout instead of
   the 112-byte reference. Positions, UVs and normals remain float32; bounded
   encodings preserve the represented attribute values. Main and shadow render
   paths accept mixed local legacy and compact catalogue geometry. Independent
   format controls use the same immutable stage and catalogue source bindings.
2. Baseline clone reuse targets warm CPU handoff work. It keeps exact proven static
   game-object clone inputs, retires scene entries in one stable batch, then
   rebuilds the original ordered baseline and collision flags. Walls/animated
   models remain fresh. Original light setup, current terrain-height sampling,
   translation and normal reconstruction still run. Exact proofs have bounded
   entries/bytes and fail back to literal construction. This is not a normals
   optimization or a bypass of source authority, readiness or input gates.
3. Bounded handoff diagnostics expose existing Java context/region/baseline phase
   hooks and sampled bridge/Worker receipt correlation. Java and browser clocks
   remain separate. Receipt-time correlation is not an exact Worker/GPU event
   timestamp. See browser-region-handoff-trace.txt and browser-baseline-reuse.txt.

Why these tracks
----------------
The frozen ac790e96 browser route had six warm bridge-silent intervals of
282/169/208/174/213/166ms. Main CPU was91.6–99% of one core while Worker use was
small, with no new GPU chunks in the warm route. Existing loadNextRegion console
summaries measured 17–25 ms, so its prepared recipe activation did not explain the
entire gap. Exact frozen generated bodies mapped normals, clone merge/vertex
hashing and repeated Scene removal work; the proof is scoped to that frozen
profile rather than reusing function IDs from an older JIT generation.

Compact geometry addresses allocation/transfer headroom rather than assuming GPU
allocation explains that CPU pause. The baseline candidate addresses a subset of
pre-bridge CPU work. Both require separate acceptance evidence.

Geometry memory and byte preservation
-------------------------------------
Complete derivative conversion checked 19,001,439 vertices and 437,033,097 decoded
float32 attribute values across all 1400 chunks. Full catalogue geometry ledger:
  Reference112-byte vertices:2,204,166,924 bytes.
  Compact48-byte vertices:     988,074,828 bytes.
  Reduction: 55.1724% including unchanged index/other geometry payloads.
These are the full geometry catalogue's potential backend bytes, not actual
resident VRAM. The private renderer still admits only bounded current coverage.

In the older frozen-JAR paired walking scene, both formats ended with 224 pinned
chunks, 110 pinned draws and 15 local draws. Pinned geometry allocation decreased
337,019,556 ->151,077,732 bytes, also 55.1724%. The broader reported backend ledger
was393,061,436 ->207,119,612 bytes (374.85 -> 197.52 MiB); this includes remaining
local resources, so its percentage differs from the pinned subset. Neither ledger
is total driver VRAM or browser system RAM. Do not market it as a total memory
reduction across every scene or device.

Fresh RAM delivery contains 46,101,734 raw source bytes plus 230,205,484 prepared
payload bytes; retained prepared primitive bytes are 229,888,400. It includes 445
recipes, 1330 query cells and 9215 model templates, with hidden roof preparation.
These payload/primitive counts exclude Java object overhead, application caches,
textures, browser processes and GPU memory. They are not a browser PSS reading.

Real compact rendering proof
-----------------------------
Firefox WebGL2 on the owner's Radeon R9 200 Series or similar ran production main
and shadow shaders in a separate hardware oracle. It checked transform-feedback
inputs and exact color/depth output for flat, textured, cutout, terrain-relief,
mixed local/catalogue and opaque/alpha-cutout shadow cases. Two actual context
generations passed 2,114,816 comparisons each, with no recorded errors. Each
cancellation case rejected stale publication and returned its ledger to zero.
Actual context recreation was exercised; this was not just a mocked context-lost
callback. Device extension availability exposed no disjoint timer query, so there
is no isolated hardware GPU-millisecond claim.

The oracle is bound to shader/driver source9ea15a0829e9d308957cad9f0acbd136679919ab
and the frozen ac790e96 dependency JAR, not the later integrated gameplay JAR. Its
production shader/layout bindings are preserved in the proof. The integrated
candidate was cooked separately as listed above. Do not silently present the old
hardware oracle as a complete new-gameplay frame pixel comparison.

Earlier real-game format comparison
-----------------------------------
Same frozen ac790e96 Java/assets and frontend; only geometryformat changed. Fixed
busy pose at 960x540, 32 fixture NPCs, coverage ready, 20 seconds stationary:
  Reference: 1193 fresh submissions / 20.092 s = 59.38 FPS; zero held.
  Compact:   1190 fresh submissions / 20.070 s = 59.29 FPS; zero held.
Both stayed focused/visible with matching pose and source epoch. Actual actor/draw
counts vary slightly between runs; this supports stability, not a strict identical
scene speedup assertion. Fresh submissions/Worker completion are not scanout or a
per-frame GPU fence. The accepted scope is this private scene on the owner's PC.

Single-pass route cold maximum completed-world interval: 635 ms reference, 569 ms
compact. Mean of five warm per-crossing maxima: 295.4 ms reference, 304.6 ms compact.
This does not establish a CPU loading improvement from compact geometry. Route
elapsed time includes polling, clicks and settling and must not become an FPS
measure. Overlapping interval rings must not be concatenated as independent
percentile samples. Compact's clear win is the geometry byte reduction.
Evidence: output/diagnostics/browser-handoff-compact/compact-comparison-1.json.

Integrated baseline-reuse acceptance
------------------------------------
PENDING: final fair OFFwarm3/ONwarm route pair, named phase/work counters and
candidate busy stationary result. The integrated OFF busy run accepted 59.26885
fresh FPS. Its earlier single cold route recorded per-leg maximum intervals
[40,521,290,355,255,297,307]ms and 53 new catalogue uploads; this is descriptive
startup evidence, not a strict pair with a later revised driver.

The initial real ON cold route recorded [40,546,343,290,276,269,305]ms. Its runtime
counters showed requested/selected=true, 3 admitted baseline replays, 3030 eligible
static clones and ZERO reused instances. It retained 86 template proofs (about
2.61 MB) with a conservative workspace peak of about 4.71 MB. Thus the exercised
runtime did not demonstrate the offline reuse reduction, and these cold results
do not establish a loading improvement. Admission or template retention alone is
not evidence that a cache avoids actual work.

The first candidate targeted legacy baseline reconstruction. Current-profile
investigation is needed to prove the higher-level owner of warm clone/normals
work; static-presentation/canonical model builders and animated replacement are
leads, not established attribution yet. Generated RSModel function identification
alone did not prove which high-level caller should have been optimized. Do not
present offline reuse counts as an exercised warm runtime optimization.

The final fair warm driver waits for three 100 ms stable-camera/input-clear samples
before the unchanged original 80 ms pointer click and requires three stable coverage
observations at route end. No engine method override, click retry or forced region
activation is used. Both final OFF and ON controls must use that same driver.
Route elapsed time includes those waits and cannot establish FPS or loading speed.

Preserved exclusions: an earlier warm route reached its last authority context but
its immediate final observer assertion raced Worker coverage ACK; passive follow-up
coverage was ready with no runtime error. A separate route missed a calibrated
minimap click while the camera was interpolating and remained at the old authority
context. These incomplete driver attempts are excluded rather than treated as new
production bugs or quietly retried into a successful sample.

Record source/epoch/ready/input/Worker receipts and bounded capacity invariants,
rather than treating low reported bridge time as a complete transition measurement.
Do not declare a loading win from offline clone counts, the old format comparison,
or a loading screen remaining hidden.
