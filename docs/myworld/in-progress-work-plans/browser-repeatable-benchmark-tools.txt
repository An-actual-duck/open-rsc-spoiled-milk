Isolation and preparation
-------------------------
prepare-repeatable.py prepares but NEVER starts a fresh empty-seed server with
copied artifacts/config/map. TCP43649/WS43549, SQLite browser_repeatable_dev and
an explicit repeatable marker are required. The runner refuses other account
rows/external services; it creates/resets only disposable browserdemo at133,660,L0,
admin1 to avoid inactivity. It never uses an owner or public database. Existing
private43629/43529 is independent. Root alone launches the server/HTTP commands.

The fixed roster is32 NPCs using8 maintained definitions: Unicorn0, Bob1, Goblin4,
Hans5, Cook7, Priest9, Man11, Traiborn17. Expected names/positions/directions are
persisted in repeatable-fixture.json; actual names/indices/positions are emitted
in status.json. Only this dedicated World suppresses other authored/lazy NPCs.
Only autonomous behavior/movement is disabled for its fixed actors. Production
client animation clocks, rendering, updates, map and network paths stay intact.
This is a controlled client workload, not a claim to reproduce public server CPU.

RepeatableCamera pins once at world-ready with cached reflection: sourcepitch912
maps to actual Scene rotation112; yaw128 maps512; zoom75; offsets and future
random-walk increments zero; automatic rotation disabled. Login/relogin renews the
pin. At that first pin only, the private helper also calls the existing public
setShowDialogMessage(false) API. The fourth counter reports actual welcomeVisible
via cached reflection. It does NOT suppress later opened UI. Do not blindly click
after this automatic close: that would become an unintended ground walk.
Ongoing samples do not repeatedly override drift. Verify actual pose,
client username and counts. The initial source112 setup produced actual912 and
was rejected without accepted timings; corrected baseline3 proved stable pose.
The parent observed37 GPU actor groups (distinct from32 server/client NPCs).
The earlier matched alignment/core cohorts retained the welcome popup: those are
matched popup-open workloads, not certified normal gameplay. Future clean timing
must assert welcomeVisible=false as well as fixed pose/count/identity.

prepare-repeatable-client.py creates a NEW immutable client stage while reusing
only a marked repeatable server. It never changes or starts that server. Full
initial preparation keeps its explicit single-source client commit contract.
The client-only helper also accepts --client-provenance for a reviewed composite:
its jarSha256 must match, singleProductionCommit must be false, the full receipt
is copied, and clientSourceCommit stays null. Never mislabel a multi-source JAR
as the base commit or frontend commit. Both preparation scripts refuse reuse of
an existing output run through the maintained staging contract.

Example preparation (root substitutes existing artifact paths):
 python3 scripts/browser-gameplay/prepare-repeatable.py --name fresh-run \
   --http-port 8160 --dependency-jar CLIENT.jar --client-source-commit EXACT40HASH
 python3 scripts/browser-gameplay/prepare-repeatable-client.py --name control-run \
   --http-port 8161 --server-run PREVIOUS_RUN --dependency-jar REVIEW.jar \
   --client-provenance REVIEW_RECEIPT.json
Use the generated repeatable-preparation.json URL/commands. Correct option spelling
is --http-port followed by a separate numeric argument. Wait for ready/status
valid and stableTicks; the HTTP stage's status path may refer to another server
run explicitly. No browser or server is started during preparation or CPU tests.

Private controls and receipts
----------------------------

Ordinary/software sessions retain their existing43629/43529 route. Query controls
geometrytransfer, regionprep, descriptorwrite and halolookup accept on/off, default OFF;

performance/correctness of the separate runtime implementations.

after pose/counters. Benchmark endpoint readers must require equality with
stats.javaWorldFrames, plus fresh readiness/identity/pose. Present and frameWork
are separate native calls; reading between them previously produced one extra
37-actor frame in a sample. Initial skewed attempts were rejected, not accepted.
Root uses numeric4096-frame measurement buffers, p95/p99/slowcounts, no screenshots
or IPC inside timed spans, fixed pose/count validation and balanced/reverse order.
Keep clean acceptance separate from profile=1 diagnostic cohorts.

diagnostics=1 additionally enables private100ms event-loop lateness and supported
longtask observations (512 rows each). Unsupported longtask APIs are reported as
unsupported, not as absence of pauses. No timers/observers when disabled. Reset
and idempotent disposal are provided. These observations DO NOT attribute delay
to GC, GPU work or Java; actual GPU timers may be unavailable in Firefox.

Native-call review staging (experimental, not an adopted runtime change)
-----------------------------------------------------------------------
The private startup query nativecalls=sync|async defaults ASYNC; ordinary and
software sessions ignore it. ASYNC keeps the literal325 frontend progress,
transition/hold and present wrapper bodies. SYNC selects generated webgl-sync.js
and four small plain-function frontend wrappers using the separately reviewed
thenable-rejecting helper. initialize remains genuinely asynchronous. Reported
module/backend dispatch metadata is retained; no support is inferred from a URL.
An unexpected Promise from a selected synchronous wrapper stops/disposes its
own session. This is not evidence that CheerpJ supports the experiment: the
manager must run the authentic JNI probe and real-game smoke before READY.

prepare.py and prepare-repeatable-client.py accept a read-only review dependency:
 --native-source /PATH/TO/REVIEWED/REPOSITORY \
 --native-source-commit EXACT40HASH
The staging helper reads ONLY three fixed regular-file Git blobs at that exact
commit: canonical webgl.js, browser-native-call-dispatch.js, and native_dispatch.py.
It never reads dirty review working-tree content or changes that repository. The
reviewed generator, not this tooling branch, owns the19-method SHA allowlist and
transformation. There is no runtime eval or duplicated maintained renderer body.
Canonical/helper/generated files and generator snapshot hashes are recorded in
stage.json.nativeDispatch, with reviewDependency=true and exact source commit.
If the ordinary current repository lacks the capability marker, no sync module
is fabricated; the existing async backend remains available. After separately
reviewed integration, default preparation can use those committed local files.
The explicitly supplied review source is independent of the dependency JAR's
multi-source receipt. Both provenances must be kept; neither is a production
single-commit build. Frozen8162/8163 are unchanged.

CPU validation additionally compares the whole frontend CSS/native/event/disposal
trace between selected ASYNC and SYNC doubles; checks plain vs Promise returns,
unexpected-thenable fail-closed behavior, exact original ASYNC wrapper bodies,
committed-file hashes, source read-only status, and rejection of invalid commit,
out-of-stage output and audited-body drift. The real production GL/error/pixel
oracle belongs to the separate native-dispatch branch. No CPU test claims actual
CheerpJ JNI compatibility, GPU pixels, FPS improvement or60FPS.
